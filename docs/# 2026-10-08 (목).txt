## 찾아보고 알게 된 것

- **`add` · `commit` · `push`를 3단계로 나누는 이유**:
    - 작업한 수많은 파일 중 이번 기록에 포함할 변경 사항만 선별(add)하고, 논리적인 작업 단위마다 의미 있는 기록(commit)을 남긴 뒤, 검증된 이력만 원격 서버에 전송(push)하기 위함임
    - 개발자가 원하지 않는 임시 파일이나 작업 중인 코드가 그대로 서버에 올라가는 것을 방지하고 체계적으로 버전을 나누기 위한 구조임을 확인함
- **핵심 개념 이해**:
    - **commit (커밋)**: 작업 디렉터리의 특정 시점 스냅샷을 로컬 저장소에 영구 기록하는 행위. 무엇을 왜 변경했는지 협업자 및 미래의 자신이 파악할 수 있도록 커밋 메시지를 필수로 남김
    - **push (푸시)**: 내 로컬 저장소(PC)에 차곡차곡 쌓인 커밋 기록들을 원격 저장소(GitHub)로 업로드하여 동기화하는 명령
- **Git의 파일 상태 관리 (3가지 상태)**:
    - **Untracked (빨강)**: Git이 한 번도 기록한 적 없는 새 파일 (커밋 대상 제외)
    - **Tracked & Modified (빨강)**: 이전에 커밋된 이력이 있으나 이후 수정된 파일 (아직 add되지 않아 수정 내용이 커밋 대상에서 제외됨)
    - **Staged (초록)**: `git add`를 통해 다음 커밋에 포함되도록 Staging Area에 선택된 상태
- **재스테이징(Re-staging)의 필요성**: 한 번 커밋되었던 파일(Tracked)이라도 내용을 수정한 뒤에는 반드시 다시 `git add`를 실행해 Staged 상태로 만들어야만 변경 사항이 커밋에 포함된다는 흐름을 확인함

## 상태 검증 및 결과 분석 (`git status`)

- **출력 결과 구조 분석**:
    - `Changes to be committed (초록)`: Staged 상태로 `git commit` 실행 시 즉시 반영되는 파일
    - `Changes not staged for commit (빨강)`: Tracked 상태이나 수정 후 아직 `git add`되지 않은 파일
    - `Untracked files (빨강)`: 신규 생성된 파일로 추적이 시작되지 않은 파일
- **분석 결과**: `git status`의 안내 문구(`use "git add <file>..."`)와 색상을 통해 커밋에 실제로 포함될 파일과 누락된 파일을 명확히 구분하여 올릴 수 있음을 확인함
