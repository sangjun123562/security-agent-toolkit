## 5교시 · 어제 명령 복습 · 서버 두 대 켜고 접속 기록 구분해 읽기

### 문제 5-1 · 어제와 같은 명령으로 서버 두 대를 켜고 접속 기록을 구분해 읽기

- (가) 내가 `web-three` 와 `web-four` 를 켠 `docker run` 명령 두 개를 붙여 넣어 주세요.
  - 쓸 내용: 윈도는 `MSYS_NO_PATHCONV=1` 부터, 맥북은 `docker run` 부터 친 그대로 두 줄
  - 답:

``MSYS_NO_PATHCONV=1 docker run -d --name web-three -p 8082:80 -v "$(pwd)/site-three:/usr/share/nginx/html:ro" nginx:1.28
MSYS_NO_PATHCONV=1 docker run -d --name web-four -p 8083:80 -v "$(pwd)/site-four:/usr/share/nginx/html:ro" nginx:1.28
```

- (나) 🔍 `docker ps` 에서 `web-three` 와 `web-four` 줄의 `PORTS` 값을 각각 적어 주세요.
  - 쓸 내용: 「web-three: … / web-four: …」
  - 답:web-three: 0.0.0.0:8082->80/tcp, [::]:8082->80/tcp

web-four: 0.0.0.0:8083->80/tcp, [::]:8083->80/tcp
- (다) 🔍 8082 로 세 번, 8083 으로 한 번 접속했을 때 `docker logs web-three` 와 `docker logs web-four` 의 `"GET / HTTP/1.1"` 줄은 각각 몇 개였고, 왜 그렇게 나뉘나요?
  - 쓸 내용: ① web-three 의 줄 수 ② web-four 의 줄 수 ③ 그렇게 나뉘는 이유(어느 포트로 온 요청이 어느 서버에 기록되는지)
  - 답:docker logs web-three에는 3개, docker logs web-four에는 1개가 남는다각 컨테이너는 독립된 네트워크 네임스페이스와 표준 출력(로그) 버퍼를 가지기 때문 내 PC의 8082번 포트로 들어온 요청은 web-three 컨테이너의 80번 포트로만 전달되어 처리되고, 8083번 포트의 요청은 web-four 컨테이너로만 전달되므로 접속 기록이 각 컨테이너에 완전히 분리되어 쌓임
- (라) 🔍 `stop` 뒤에 `docker ps` 와 `docker ps -a` 에서 두 서버가 각각 어떻게 보였고, `rm` 뒤에는 어떻게 되었나요?
  - 쓸 내용: 「stop 뒤 ps: … / stop 뒤 ps -a: … / rm 뒤 ps -a: …」
  - 답:docker stop 실행 후: docker ps에서는 두 컨테이너가 모두 사라져 보이지 않지만, docker ps -a로 조회하면 두 서버 모두 STATUS가 Exited (0) 상태로 남아 있다   docker rm 실행 후: docker ps -a 목록에서도 web-three와 web-four 줄이 완전히 삭제되어 더 이상 나타나지 않음
- (한 줄) 보안 담당에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 보안 담당이 바로 읽을 수 있는 한 문장(서버를 몇 대 어떻게 켰고 기록이 어떻게 남았는지)
  - 답:포트(8082, 8083)와 볼륨 경로를 분리하여 고객용과 직원용 서버를 독립 구동했으며, 각 서버별로 접속 로그(docker logs)가 격리되어 기록됨을 검증 완료하여 이상 접속 발생 시 대상 페이지를 즉시 식별할 수 있다
- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답:동일한 도커 이미지를 기반으로 구동하더라도 포트 포워딩과 볼륨 마운트 분기를 통해 컨테이너별 서비스 환경과 감사 로그를 완전히 독립적으로 통제할 수 있다는 점을 배웠고 대화형 셸 진입 없이 docker exec 로 단일 명령을 즉시 실행하는 운영 팁을 익혔다 

## 6교시 · 내 이미지 만들기 (Dockerfile)

### 문제 6-1 · Dockerfile 두 줄을 써서 내 이미지 만들기

- (가) 내가 쓴 Dockerfile 두 줄을 붙여 넣어 주세요.
  - 쓸 내용: Dockerfile 두 줄(`FROM` 줄 · `COPY` 줄)
  - 답:

```
FROM nginx:1.28
COPY site-three/index.html /usr/share/nginx/html/index.html

```

- (나) 🔍 `FROM` 과 `COPY` 가 각각 하는 일을 적어 주세요.
  - 쓸 내용: ① FROM 이 하는 일 ② COPY 가 하는 일
  - 답:프롬은 새 이미지를 만들때 기반이 될 기존 부모 이미지를 지정한다 from ngin:1.28은 공식 nginx 웹 서버 프로그램과 기본 시스템 파일들을 새 이미지의 밑바탕으로 그대로 포함 하겠다는 의미이다 카피는 내호스트 pc의 특정 파일이나 디렉터리를 이미지 내부의 지정된 경로로 복사한다 카피의 내용은 내 pc의 html문서를 nginx 웹 서버가 기본으로 서비스하는 index.html위치로 덮어 씌워 이미지 자체에 포함 시킨다 
- (다) 🔍 5교시와 달리 `docker run` 에 `-v` 가 없는데도 내 화면이 나오는 이유는 무엇인가요?
  - 쓸 내용: ① 어제 파일이 컨테이너에 닿던 방법 ② 오늘 파일이 서버에 있는 위치와 시점
  - 답:5교시에는 호스트 pc의 로컬 폴더를 컨테이너 실행시 실시간으로 연결 해주어야 했지만 이번에는 docker build 과정에서 copy 명령어를 통해 안내 페이지 파일이 새이미지 내부 파일 시스템에 이미 영구적으로 복사 되었기 때문이다 따라서 외부 볼륨 마운트 없이 이미지 단독으로 실행해도 내페이지가 바로 서비스 된다 
- (라) 🔍 `docker build` 출력에서 `[2/2] COPY` 줄과 `naming to` 줄을 붙여 넣고, 각각 무엇을 알려 주는지 적어 주세요.
  - 쓸 내용: ① 두 줄 ② 각 줄이 알려 주는 것
  - 답:첫 줄은 도커 파일의 두번째 단계인 파일 복사 작업이 정상 수행되어 내pc의 site-three/index.html 파일이 이미지 안의 목적지 경로로 성공적으로 주입되었다는걸 알려준다 두번째 줄은 레이어 빌드 및 이미지 내보내기가 완료되어 완성된 새이미지 객체에 사용자가 지정한 이름과 태그인 my-nginx:1 이 성공적으로 부여 되었음을 알려준다 

```
=> [2/2] COPY site-three/index.html /usr/share/nginx/html/index.html
=> => naming to docker.io/library/my-nginx:1
```


## 7교시 · 이미지 버전 다루기 · 되돌리기 · 정리 · 올리기

### 문제 7-1 · 파일을 고쳐 보고, 이미지를 다시 만들어 반영하기

- (가) 파일을 고친 직후 새로 고침했을 때 화면에 무엇이 나왔나요?
  - 쓸 내용: 새로 고침했을 때 보인 화면의 큰 제목
  - 답:site-three와 고객안내페이지 입니다 문구가 그대로 나타남
- (나) 🔍 파일을 고쳤는데도 화면이 바뀌지 않은 이유와, 바꾸려면 무엇을 해야 하는지 적어 주세요.
  - 쓸 내용: ① 바뀌지 않은 이유(서버가 보는 파일이 어디 있는지) ② 바꾸려면 할 일
  - 답: 컨테이너가 실행중인 기반 이미지는 빌드 시점의 파일 내용이 고정된 읽기 전용 상태이고 호스트 피시와 실시간으로 마운트 된것이 아니라 이미지 내부에 복사되어 들어간 파일이기 때문 바꾸기 위해선 고친파일을 포함 하도록 새 태그를 지정해 이미지를 다시 빌드 한 후 기존 컨테이너를 제거 하고 새로 빌드된 이미지로 컨테이너를 다시 켜야한다 
- (다) 🔍 5교시의 `-v` 방식과 6교시의 이미지에 넣는 방식은 파일을 고쳤을 때 반영되는 방법이 어떻게 다른가요?
  - 쓸 내용: ① -v 방식의 반영 방법 ② 이미지에 넣는 방식의 반영 방법
  - 답:-v: 호스트 디렉터리가 컨테이너와 실시간으로 연결되어 있으므로 호스트에서 파일을 수정하고 브러우저를 새로고침 하기만 하면 즉시 변경 내용이 반영됨/ 이미지 포함 방식: 파일이 이미지 레이어에 패키징 되어있으므로 파일을 수정한 뒤 반드시 도커 이미지를 다시 빌드하고 컨테이너를 재생성 해야하만 변경 사항이 반영됨 

### 문제 7-2 · 이전 버전으로 되돌리고 쓰지 않는 이미지 지우기

- (가) 이전 버전으로 되돌린 뒤 `docker ps` 의 `IMAGE` 칸 값과 브라우저에 나온 제목을 적어 주세요.
  - 쓸 내용: 「IMAGE: … / 브라우저 제목: …」
  - 답:my-nginx:1 / site-three
- (나) 🔍 쓰고 있는 `my-nginx:1` 을 `docker rmi` 로 지우려 했을 때 에러 문구의 핵심과, 어떻게 해결했는지 적어 주세요.
  - 쓸 내용: ① 에러 문구의 핵심 ② 지워지지 않은 이유 ③ 해결한 순서
  - 답:Error response from daemon: conflict: unable to delete my-nginx:1 (must be forced) - container 5a577edce940 is using its referenced image b422cc467468
  해당 이미지를 참조하고 있는 my-site 컨테이너를 먼저 삭제 하여 의존성을 해체한뒤 docker rmi my-nginx:1 명령을 실행해 이미지를 안전한게 삭제 했음 
- (다) 🔍 이미지에 `:1` · `:2` 같은 태그를 붙여 두면 문제가 생겼을 때 어떤 점이 좋은가요?
  - 쓸 내용: ① 되돌리는 방법 ② 어느 버전이 켜져 있는지 아는 방법
  - 답:소스커드를 이전 상태로 다시 수정하거나 재빌드하는 복잡한 과정 없이 안정성이 검증된 이전 버전의 태그를 지정해 docker run을 실행하는 것 만으로도 몇초만에 즉각적인 서비스 롤백이 가능하다 
- (한 줄) 보안 담당에게 보낼 답을 한 문장으로 적어 주세요.
  - 쓸 내용: 보안 담당이 바로 읽을 수 있는 한 문장(되돌린 일과 정리한 일)
  - 답:안내 페이지 수정 사항을 태그버전으로 새 빌드하여 정상 반영 완료 했으며 장애 발생 시 즉각 롤백 가능한 태그 기반 복구 절차 검증 및 미사용 도커 이미지 정리를 완료 함
- 이 교시에서 새로 알게 된 것 하나를 적어 주세요.
  - 쓸 내용: 자유롭게
  - 답: 도커 이미지의 불변성 원리와 버전 태그를 활용한 무중단 롤백 메커니즘을 알았고 실행 중인 컨테이너와 이미지 간의 참조 중속성으로 인해 컨테이너를 먼저 정리해야 이미지가 삭제 된다는 원칙을 배웠다
