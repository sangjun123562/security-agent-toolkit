## 5교시 · 업무 시간과 접속 위치 조건으로 판정하기

### 문제 5-1 · 기본 판정 뒤에 업무 시간과 접속 위치 조건을 확인하기

- (가) 실행한 출력 전체를 붙여 넣고, 허용된 요청과 거부된 요청이 각각 몇 건인지, 조건 때문에 거부된 요청이 몇 건이고 몇 번인지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 허용 · 거부 건수 ③ 조건 때문에 거부된 요청의 건수와 번호
  - 답:허용: 3건 거부: 5건 / 총4건/3,4,5,7

```
--- 단계 1: 판정 - 요청 8 건
1 seoyeon SALES:QUERY office 10:00 -> 허용(역할 권한)
2 seoyeon SALES:CHANGE office 09:00 -> 허용(역할 권한)
3 seoyeon SALES:CHANGE office 18:00 -> 거부(업무 시간 밖)
4 seoyeon SALES:CHANGE external 10:00 -> 거부(혀용되지 않은 접속 위치)
5 seoyeon SALES:CHANGE external 22:00 -> 거부(업무 시간 밖)
6 junho SETTLE:QUERY vpn 19:30 -> 허용(역할 권한)
7 gaeun ACCOUNT:CHANGE vpn 10:00 -> 거부(혀용되지 않은 접속 위치)
8 dami SALES:QUERY office 10:00 -> 거부(퇴사한 계정)
--- 단계 2: 확인 - 조건 파일에 적힌 조건
SALES:CHANGE | 9시부터 18시 전까지 | office, vpn
SETTLE:QUERY | 8시부터 20시 전까지 | office, vpn
ACCOUNT:CHANGE | 9시부터 18시 전까지 | office
```

- (나) 🔍 5번 요청(seoyeon, 외부, 22시)은 업무 시간도 접속 위치도 어긋나는데 거부 이유는 「업무 시간 밖」 하나만 나옵니다. 거부 이유를 하나만 알려 주는 것과 어긋난 조건을 모두 알려 주는 것 중, 요청한 사람이 정상 사용자인 경우와 계정을 가로챈 사람인 경우 각각 어느 쪽이 나은지, 판정 결과를 점검하는 관제 담당자에게는 어느 쪽이 나은지 이유와 함께 적어 주세요.
  - 쓸 내용: ① 정상 사용자에게 나은 쪽과 이유 ② 계정을 가로챈 사람에게 나은 쪽과 이유 ③ 관제 담당자에게 나은 쪽과 이유
  - 답:정상 사용자의 경우: 어긋난 조건을 모두 알려주는 쪽이 유리합니다 "시간도 지났고 외부망 접속도 안됨" 을 모두 알아야 내일 출근해서 사내망으로 접속하거나 조치를 취할 수 있어 업무 혼선을 줄입니다.
  가로챈 공격자: 이유를 하나만 알려 주거나 최소한의 정보만 주는 쪽이 낫습니다 공격자에게 모든 보안 통제 정책을 노출하면 공격자가 vpn을 타고 업무시간에 다시 시도해야겠군 처럼 방어망을 우회할 힌트를 얻게 되기 때문입니다 
  관제 담당자의 경우 : 어긋난 조건을 모두 기록/확인할 수 았는 쪽이 낫습니다 이상징후 분석 시 단순 실수인지 복합적인 정책 위반을 동반한 침해 시도인지 정확하게 파악하고 대응 할 수 있기 때문입니다.

- (다) 🔍 seoyeon 의 계정을 다른 사람이 새벽 2시에 외부에서 쓰려 한다고 해 봅시다. 계정에 `SALES:CHANGE` 역할 권한이 있는데도 이 요청을 거부해야 하는 이유와, 로그인할 때 한 번만 확인하고 그 뒤 요청은 확인하지 않았다면 어떻게 되었을지 적어 주세요.
  - 쓸 내용: ① 거부해야 하는 이유 ② 로그인 때 한 번만 확인했다면 생길 일
  - 답:권한이 있는데도 거부해야 하는 이유 : 정상 직원이더라도 새벽 2시 외부접속은 자격증명이 탈취 되었을 가능성이 매오 높은 비정상 행위기 때문입니다 중요 데이터 변경 권한은 특히 엄격한 환경 조건으로 공격 표면을 줄여야 피해를 막을 수 있습니다.
  로그인시 1회만 검증하고 이후 검증하지 않았다면 : 정상적으로 회사에서 로긍ㄴ해 둔 세션을 탈취하거나 세션 토큰이 유효한 상태로 외부에 연결 된 경우 공격자가 아무런 제약 없이 새벽 시간에 데이터를 위조 변조 할 수 있게 됩니다 

## 6교시 · 판정 서버 만들고 요청 로그 남기기

### 문제 6-1 · 판정 서버를 만들고 요청마다 로그 남기기

- (가) 터미널 2의 출력 전체를 붙여 넣고, 응답의 상태 코드별 건수(200 · 403 · 400)와 서버가 남긴 로그 줄 수를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 상태 코드별 건수 ③ 로그 줄 수
  - 답:200: 3건 /403: 5건 /400: 1건/8줄

```
--- 단계 1: 응답 - 요청 9 건
1 seoyeon SALES:CHANGE -> 200 역할 권한
2 seoyeon SALES:CHANGE -> 403 업무 시간 밖
3 seoyeon SALES:CHANGE -> 403 혀용되지 않은 접속 위치
4 seoyeon SALES:QUERY -> 200 역할 권한
5 junho SETTLE:QUERY -> 200 역할 권한
6 junho SETTLE:QUERY -> 403 혀용되지 않은 접속 위치
7 gaeun ACCOUNT:CHANGE -> 403 혀용되지 않은 접속 위치
8 dami SALES:QUERY -> 403 퇴사한 계정
9 seoyeon SALES:CHANGE -> 400 입력이 잘못됨
--- 단계 2: 로그 - 서버가 남긴 8 줄
seoyeon SALES:CHANGE office 2026-10-30T09:00 -> True 역할 권한
seoyeon SALES:CHANGE office 2026-10-30T18:00 -> False 업무 시간 밖
seoyeon SALES:CHANGE external 2026-10-30T10:00 -> False 혀용되지 않은 접속 위치
seoyeon SALES:QUERY external 2026-10-30T23:00 -> True 역할 권한
junho SETTLE:QUERY vpn 2026-10-30T19:30 -> True 역할 권한
junho SETTLE:QUERY external 2026-10-30T10:00 -> False 혀용되지 않은 접속 위치
gaeun ACCOUNT:CHANGE vpn 2026-10-30T10:00 -> False 혀용되지 않은 접속 위치
dami SALES:QUERY office 2026-10-30T10:00 -> False 퇴사한 계정
--- 단계 3: 대조 - 판정까지 간 응답과 로그
판정까지 간 응답 8 건 / 로그에 남은 줄 8 줄
```

- (나) 🔍 거부는 403, 값이 빠진 요청은 400 으로 상태 코드를 다르게 답했습니다. 요청을 보내는 쪽이 이 둘을 구별해야 하는 이유와, 구별하지 않으면 생길 수 있는 일을 적어 주세요.
  - 쓸 내용: ① 구별해야 하는 이유 ② 구별하지 않을 때 생길 수 있는 일
  - 답:403: 요청 규격은 정상이나 해당 사용자의 인가가 거부된 것이므로 호출자는 접근 불가로 처리하고 권한 신청이나 업무환경 변경을 안내해야 합니다
  400: 파라미터 누락이나 데이터 형식 오류 등 호출 프로그램 자체의 개박 전송 버그이므로 프로그램 코드를 수정해 규격에 맞게 다시 보내야 합니다 
  구별하지 않을때 생기는 문제: 클라이언트가 400과 403을 뭉뚱그려 권한없음으로 간주하면 단순 파라미터 오타나 누락으로 인한 프로그램 버그를 권한 문제로 오인해 불필요한 권한 신청을 남발하거나 시스템 디버깅이 불가능 해집니다

- (다) 🔍 서버 로그를 요청마다 새로 쓰면(`"w"` 모드) 한 달 뒤에 지난주의 거부 기록을 찾으려 할 때 어떻게 되나요? 로그에는 끝에 덧붙이는 방식이 알맞은 이유를 적어 주세요.
  - 쓸 내용: ① `"w"` 모드일 때 생기는 일 ② 덧붙이는 방식이 알맞은 이유
  - 답:w: w모드는 파일에 쓸때마다 기존 내용을 전부 지우고 덮어쓰므로 항상 가장 마지막에 들어온 1건의 요청만 남고 이전의 모든 기록이 완전히 유실되어 지난주의 거부 기록을 찾을 수 없습니다.
  a: 보안 감사와 관제 로그는 시간에 따라 발생한 모든 요청의 누적 이력이 시간순으로 완전하게 보존되어야 침해 사고 분석이나 컴플라이언스 점검이 가능하므로 기존파일 끝에 계속 이어 쓰는 a모드가 필수적 입니다.
