## 2교시 · 권한 요청서 만들기

### 문제 2-1 · 요청서를 만들어 목록에 모으고, 접수할 수 없는 요청 걸러 내기

- (가) 실행한 출력 전체를 붙여 넣고, 접수되지 않은 세 건이 각각 `create_request` 의 어느 `if` 조건 때문에 접수되지 않았는지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 접수되지 않은 세 건 각각이 걸린 `if` 조건

seoyeon SETTLE QUERY -> 접수됨, 요청 번호 1

- (나) 🔍 요청서의 `until`(희망 만료 시각)은 요청자가 직접 적습니다. 요청자가 적은 기간을 그대로 믿고 승인해도 될까요? 승인하기 전에 확인할 것을 두 가지 이상 적어 주세요.

  요청 사유에 적힌 작업을 끝내는 데 실제로 며칠이 소요되는지 프로젝트 일정을 확인한다 
  회사의 정보보안 규정상 임시 예외 권한에 허용된 최대기간 을 초과하지 않는지 확인한다 

## 3교시 · 승인과 반려

### 문제 3-1 · 승인 · 반려 함수 만들고, 두 번째 처리가 막히는지 확인하기

- (가) 실행한 출력 전체를 붙여 넣고, 막힌 세 줄이 각각 왜 막혔는지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 막힌 세 줄 각각의 이유
  - 답1본인 승인 -> False 검토 중이 아님:요청자와 승인자가 동일하여 자가 승인 방지 규칙에 걸렸다 ,1승인 -> False 검토 중이 아님: 1번요청서는 바로앞에 이미 승인되어 상태가 approved 로 변경되어서 reviewing 상ㅌㅐ가 아니라서 중복 승인이 차단됨 ,2승인 -> False 검토 중이 아님 2반요청서는 앞에 이미 반려가되어 상태가 rejected 로 확정되어 reviewing 상태가 아니라서 반려후 재승인이 차단됨

```
--- 단계 1: 처리 - 본인 요청 시험 한 건, 승인 · 반려 여섯 건을 처리한다
1 본인 승인 -> False 검토 중이 아님
1 승인 -> False 검토 중이 아님
2 반려 -> True 반려
3 승인 -> False 검토 중이 아님
4 승인 -> False 검토 중이 아님
1 승인 -> False 검토 중이 아님
2 승인 -> False 검토 중이 아님
--- 단계 2: 점검 - 요청서 목록
1 seoyeon reviewing None
2 gaeun rejected security_manager
3 dami reviewing None
4 junho reviewing None
```

- (나) 🔍 이미 승인한 요청서를 다시 승인하지 못하게 막는 이유는 무엇인가요? 막지 않으면 어떤 일이 생길 수 있나요?
  - 쓸 내용: ① 막는 이유 ② 막지 않을 때 생길 수 있는 일
  - 답:요청서의 상태머신 일관성을 유지하고 한건의 신청 건에 대해 예외 권한이 중복 부여되거나 기간,이력이 꼬이는 데이터 훼손을 방지하기 위해
  미방지시 생기는 일은 동일 요청서에 대해 중복된 예외 아이디가 여러 개 생성되어 불필요한 예외 권한이 시스템에 복수로 등록 되거나 감사 로그 상에서 한 요청에 대해 다중 승인 이력이 남아 승인 시점과 관리 책임 소재가 불분명 해짐

- (다) 🔍 `approve_request` 에서 `request["user"] == approver` 검사를 뺀다면 어떤 위험이 생길까요? 요청자가 친구에게 대신 승인해 달라고 부탁하면 이 검사로는 막을 수 없습니다. 이런 경우를 막으려면 무엇이 더 필요할까요?
  - 쓸 내용: ① 검사를 뺐을 때의 위험 ② 더 필요한 장치 한 가지 이상
  - 답:권한이 필요한 사용자 본인이 시스템이 직접 승인자로 로그인하거나 api를 호출해 스스로의 권한을 승인하는 자가 승인이 가능해져 직무분리가 무너지고 권한 오남용 및 내부자 횡령/유출 통제가 불가능해짐/ 고권한 예외 권한에 대해서는 직속 부서장 1차 승인 후 보안 부서의 2차 교차 승인이 반드시 필요하도록 승인 단계를 복수화 시킨다 

## 4교시 · 정책 확인 후 예외 권한 부여

### 문제 4-1 · 승인된 요청서를 정책으로 확인하고 예외 권한 부여하기

- (가) 실행한 출력 전체를 붙여 넣고, 부여를 시도한 네 건이 각각 어떻게 됐는지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 네 건 각각의 결과
  - 답:서연: 정상 승인 상태이고 직무상 권한만 없던 정상 재직자이므로 정상적으로 예외 6번이 부여되고 상태가 granted로 변경됨/가은: 3교시에서 관리자에 의해 이미 반려 되었으므로 승인되지 않은 요청으로 분류되어 부여 거부됨/다미:승인자는 승인했으나 코드 정책 확인 시 퇴사자로 판정되어 부여 거부됨/준호:승인자는 승인 했으나 이미 역할 자체에 해당 권한이 존재하므로 부여 거부됨

```
--- 단계 1: 판정 - 부여 전
1 seoyeon SETTLE:QUERY -> False 권한 없음
2 gaeun SALES:QUERY -> False 권한 없음
3 dami SALES:QUERY -> False 퇴사한 계정
4 junho SETTLE:QUERY -> True 역할 권한
--- 단계 2: 부여 - 요청서마다 부여를 시도한다
1 seoyeon reviewing -> False 승인되지 않음
2 gaeun rejected -> False 승인되지 않음
3 dami reviewing -> False 승인되지 않음
4 junho reviewing -> False 승인되지 않음
--- 단계 3: 점검 - 부여 후
1 seoyeon SETTLE:QUERY -> False 권한 없음
2 gaeun SALES:QUERY -> False 권한 없음
3 dami SALES:QUERY -> False 퇴사한 계정
4 junho SETTLE:QUERY -> True 역할 권한
```

- (나) 🔍 승인자가 승인한 3번 요청(`dami`)을 코드가 부여하지 않았습니다. 코드의 이 확인이 없었다면 어떤 일이 생겼을까요? 승인자가 이 문제를 미리 막기 어려운 이유도 적어 주세요.
  - 쓸 내용: ① 확인이 없을 때 생기는 일 ② 승인자가 미리 막기 어려운 이유
  - 답:코드 확인이 없었을때는 승인자가 승인했다는 이유만으로 예외 목록에 그대로 추가되어 퇴사한 직원이 인수인계를 빌미로 사내 민감 영업 실적을 무단 열람할 수 있는 심각한 보안 유출 사고가 발생 했을것이다
  승인자가 사전에 막기 어려운 이유는 승인자는 결제 화면에서 신청자가 작성한 사유와 업무 타당성 위주로 컴토하기 쉬우며 인사 시스템 상의 실시간 재직/퇴사 상태를 매 결제 건마다 일일이 조회해 보기 어렵기 때문이다 

- (다) 🔍 부여한 예외의 만료 시각에는 요청서의 희망 만료 시각을 그대로 썼습니다. 그 시각이 지나면 이 예외는 어떻게 될까요? 만료된 예외를 정리하는 점검은 누가 얼마나 자주 하면 좋을까요?
  - 쓸 내용: ① 만료 뒤 예외가 어떻게 되는지 ② 점검을 누가 얼마나 자주 할지
  - 답:만료 시각 경과 후의 동작: 판정 엔진 내부에서 now < expires 조건을 검사하므로, 정해진 희망 만료 시각이지나는 즉시 자동으로 비활성화되어 조회가 전면 거부(권한 없음) 처리됩니다.
